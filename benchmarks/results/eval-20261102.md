# Comparison with external engines, 2026-11-02 (with elk-rs and the layered construction)

Machine: Apple M3, node v24.21.0, `layout-command` release build, revision 437d5bc plus the harness change. `node
compare.mjs --limit 150 --repeat 3`: every engine gets Layerweave's bounded view of each dataset (up to 150 nodes, leaves
180 × 54); one metric implementation scores every output; times are medians of 3 runs. Layerweave's times include a process
start and a JSON round trip, the others are in-process (elk-rs through its native addon): compare orders of magnitude only.
The machine was not idle.

Engines: Layerweave default and with `layeredConstruction` (each initial and refined); `elkjs` 0.12.0 and `elk-rs`
(`@openedges/elk-layout` 0.12.1, Rust port of ELK 0.12.0, commit eb586b6 of github.com/openedges/elk-rs, EPL-2.0 OR
GPL-3.0-or-later; evaluation only, nothing copied) with layered, orthogonal routing and `INCLUDE_CHILDREN`; dagre 3.1.1.

Best per dataset (fewest hits, then crossings, then bends; ties count for all): elkjs 17, elk-rs 14, Layerweave layered 10,
Layerweave 8.

Reading:
- The layered construction moves Layerweave towards ELK: crossings −16 %, bends −20 % (fewer bends than ELK in total),
  refinement about 3× faster. Crossings stay 21 % above elkjs; the largest gaps are layerweave-code (2040 against 1611),
  workflow-dag (585 / 249), org-chart (55 / 18) and synthetic-2k (3409 / 3165).
- Layerweave's line–node hits come almost all from views with straight edges (mixed-large 88, petri-net-shapes 49,
  mixed-layouts 9, self-loops 9): the organic and tree views are drawn straight (0 bends) and are not like for like with
  ELK's orthogonal routes.
- elk-rs draws nearly what elkjs draws (crossings 6138 against 5894, bends 5358 against 5548) at about a sixth of the time.

## JSON transfer against computation (for the persistent-engine question)

Whole `layout-command` calls on layerweave-code with the layered construction (7 runs, median):

- view 100, layered: snapshot 367 KB (126 nodes, 184 routes); JS stringify 0.7 ms, parse 0.8 ms; process without snapshot 1.9 ms; read snapshot only (intent) 4.3 ms; add edit 130.0 ms
- budget 50, layered: snapshot 485 KB (67 nodes, 159 routes); JS stringify 0.7 ms, parse 0.9 ms; process without snapshot 2.0 ms; read snapshot only (intent) 4.9 ms; add edit 340.2 ms

The transfer (JSON in JavaScript about 1.5 ms, reading the snapshot in the engine about 2.5 ms) is 1–3 % of an edit at this
size; the computation dominates. The view within a budget carries the whole source graph in every snapshot (485 KB for 67
visible nodes), which grows with the model, not with the view.
