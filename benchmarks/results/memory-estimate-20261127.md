# The estimate of a request's peak memory against the measured peak, 2026-11-27

Question (#224, ADR 0024 step C3): how close does `estimate` come to the peak a request reaches, per operation and per
target, and what does the estimate itself cost?

## Machine, build, load

- Apple M3 (8 cores, 16 GB), macOS 26.0, rustc 1.99.0, Node v24.21.0.
- Revision: branch `memory-estimate` on `origin/main` 6aee0e3; the measured engine is that change before its
  coefficients were fitted (the peaks do not depend on them, the sizes the estimate reads neither).
- Native: `benchmarks/session-memory`, binary `request-peak`, `--release` (no LTO), with a counting allocator: heap
  bytes requested and not yet freed, counted exactly, so the machine's load does not change them. WASM:
  `arqlet-wasm`, `--release --features query` (the playground's build), in Node, a fresh instance per request.
- Load: very high and changing, other agents were building on the machine. One-minute load averages, recorded per row:
  25 to 120 for the native rows, 28 to 146 for the WASM rows. Memory counts do not depend on it; every time below is a
  single observation under that load, not a performance figure.

## What was measured

- Graphs: 28 reference datasets of `benchmarks/generate.py` (limit 100, default options); the synthetic graphs of
  `generate.py::synthetic` with 2k, 5k, 20k, 50k and 114k nodes (limit 100 with `levelOfDetail: {depth: 0}`, limit 300
  with depth 1; 2k, 5k and 20k also at limit 1 000 without levels, 2k laid out whole); `full-1000` and `full-3000`
  (containers of ten, 1.3 edges per node, laid out whole, the shape of PR #232's measurement); the code indexes of
  `benchmarks/overview/generate.py` with 10k, 50k and 100k nodes (limit 100, depth 0, and the overview). Generated by
  `benchmarks/memory-estimate/datasets.py`.
- Requests: the import; on its snapshot a `toggle` (the collapsed container with the median number of children, else
  closing the largest), `direction`, a `patch` of ten nodes and ten edges, `refine` with `workBudget: 4` on one and four
  threads; the overview of the whole graph. Each through `dispatch` (the text with its snapshot) and in a resident session
  (the import, then each edit on the session's current view, `scene: false`).
- Native peak: counted heap above what was live before the request text was built (the text counts). Native layout
  peak: laying out the view after the request from scratch, alone (`arqlet_layout::compute`), the basis of the layout
  model. WASM peak: the growth of the linear memory of a fresh instance (what a worker keeps), and the counted heap peak
  (`heapPeakBytes`, new in this change); for a session's edits, which run in an instance that loaded the snapshot first
  (whose growth the load hides), the counted peak.
- Raw rows: `memory-estimate-20261127-native.jsonl` (570), `memory-estimate-20261127-wasm.jsonl` (419). The WASM sweep
  was cut short under the load: the 114k synthetic graph, synthetic-50k at depth 1, the reference rows of PR #232's
  shape at limit 1 000 and code-100000 are measured natively only.

```sh
python3 benchmarks/memory-estimate/datasets.py
CARGO_TARGET_DIR=target cargo build --release --manifest-path benchmarks/session-memory/Cargo.toml --bin request-peak
python3 benchmarks/memory-estimate/sweep.py native.jsonl
cargo build -p arqlet-wasm --target wasm32-unknown-unknown --release --features query --locked
python3 benchmarks/memory-estimate/sweep.py wasm.jsonl --wasm target/wasm32-unknown-unknown/release/arqlet_wasm.wasm
python3 benchmarks/memory-estimate/fit.py report native.jsonl wasm.jsonl [--holdout code-50000,synthetic-50k]
```

## The model

`estimate` reads the request into its types and finds the view the operation lays out the way the operation finds it,
without laying out: an import runs its selection and projection (`prepare_import`, split from the import without a
change), `toggle`, `reveal`, `filter`, `configure` and `restore` project the view after them, `patch` and `add` add what
they bring, the other edits keep the view. The answer adds four parts:

- `request`: the request text;
- `input`: `(text − 1) · text bytes + base` (reading the request, the JSON value the protocol reads a snapshot request
  into first, writing the answer);
- `structure`: `source · heap of the source graph` (its index, the selection, copies), for the overview also per node
  and per edge;
- `layout`: `share · jobs · L(view)`, where `L` is the peak of laying out the view from scratch, fixed plus per node,
  edge, open container, edge squared, edge squared over nodes (many edges gathered between few boxes), node times open
  container and open container squared (deep and wide hierarchies), and `jobs` the refinement's threads.

The coefficients are per kind of operation (import, overview, `open` for the edits that change what the view shows,
`keep` for those that keep it, `patch`, `refine`) and place (dispatch, session), and per target: each build estimates for
itself (`target`: `native64` or `wasm32`), since type sizes differ. They are fitted by `fit.py` so that the ratio
estimate / measured is as even as possible over the requests above 4 MB (a seeded random search, deterministic), raised to
bound every calibration row, and then multiplied by a margin of 1.15 (`MARGIN`, on everything but the text), justified
by the held-out graphs below. A refinement's layout share is set to that of `keep` (the calibration's small work budget
lays out little; the larger views refuse a refinement anyway, "Prototype refinement size limit exceeded").

Below 4 MB the estimate is often several times the peak (a fixed part of a few hundred kilobytes to a few megabytes);
that matters little for admission and is not in the factors. The worst overestimates come from where the from-scratch
layout bounds an edit that continues the earlier layout (`direction` on the dense 50k and 114k first views: 340 MB
measured, about 3.6 GB estimated), from refinements (the work budget lays out little; four threads are counted as four
layouts, the measurement shows them mostly serial), and from the layout itself: two views of almost the same size
(synthetic-5k and synthetic-20k at limit 1 000, 1 435 and 1 710 nodes, 435 and 710 open containers) peak at 33 MB and
222 MB, and no size the estimate reads tells them apart, so the smaller one is estimated about five times too high.

## Graphs left out of the fit

The factors above are in-sample. Two checks fitted without some graphs and measured on them (without the margin; with it,
multiply the rest of the estimate by 1.15):

- **Interpolation** (fitted without code-50000 and synthetic-50k, whose neighbours code-10000, code-100000, synthetic-20k
  and synthetic-114k stay): natively the lowest ratio is 0.93 (synthetic-50k at depth 1, session edits), median 1.07 to
  1.56; in WASM 0.88 (code-50000, dispatch toggle) on requests above 4 MB, and 0.55 on a session toggle of 9 MB. With the
  margin of 1.15 every native row and every WASM row above 10 MB is covered; that is where the margin comes from.
- **Extrapolation** (fitted without all three code indexes and synthetic-50k): the code indexes have a large source graph
  and a small view, a shape no other calibration graph has. The estimate then falls to 0.26 to 0.5 of the peak of
  dispatch edits on them (code-100000 `direction`: 26.6 MB estimated, 99.9 MB measured): it had explained the synthetic
  graphs' cost through their view, which grows with their source. The estimate is only as good as the shapes it was
  calibrated on; a host whose graphs have another shape should check it against `heapPeakBytes` (WASM) or its own
  counts, and recalibrate (`fit.py`) when it falls short.

## Native and WASM

On the same requests the WASM engine's linear memory and the native counted heap are close (synthetic-50k first view:
507 MB linear against 561 MB counted; full-3000: 262 against 284 MB); the linear memory is 1.2 to 1.35 times the
counted WASM heap (allocator overhead and pages). PR #232 found the native resident memory of a 3 000-node import at
610 MB against 340 MB in WASM; the resident memory of `layout-command` against the counted heap is in the next section.

## Resident memory of the native engine

The estimate bounds counted heap bytes. What the operating system sees is more: one `layout-command` process per request
(release build of this change with its coefficients), its peak resident set size from `/usr/bin/time -l`, less that of a
trivial request (3 MB). Load average about 45 to 50 (`benchmarks/memory-estimate/rss.py`, raw rows
`memory-estimate-20261127-rss.jsonl`; the edit is a toggle of the first collapsed container, else `direction`):

| Request | Resident, above the base | Estimate (counted heap) | Resident / estimate |
|---|---|---|---|
| synthetic-2k import, depth 0 | 17 MB | 10 MB | 1.7 |
| synthetic-20k import, depth 0 | 205 MB | 191 MB | 1.07 |
| synthetic-20k toggle | 219 MB | 94 MB | 2.3 |
| full-1000 import | 139 MB | 60 MB | 2.3 |
| full-1000 direction | 160 MB | 57 MB | 2.8 |
| full-3000 import | 662 MB | 327 MB | 2.0 |
| full-3000 direction | 808 MB | 314 MB | 2.6 |
| code-50000 import, depth 0 | 180 MB | 157 MB | 1.15 |
| code-50000 toggle | 200 MB | 67 MB | 3.0 |

On macOS's system allocator the resident memory of a native request is up to 3 times its counted heap (full-3000
`direction`: 201 MB counted, 808 MB resident): freed blocks are not handed back at once and the many small allocations of
a layout fragment. The native estimate is therefore not a bound on resident memory; a host that admits native work by
resident memory multiplies it (3 on this machine) or measures its own allocator. In WASM the estimate bounds the linear
memory itself.

The estimates of the final build were also checked against a fresh measurement on synthetic-20k (limit 100, depth 0)
and full-1000, natively and in WASM: the same ratios as in the tables (for example 1.81 for the import, 1.14 for the WASM
overview, 13.67 for a session's refinement), every estimate above its peak.

## What the estimate costs

Its own time and counted peak, native, on the largest requests (single observations under the load above):

| Request | Request: time, peak | Estimate: time, own peak |
|---|---|---|
| import synthetic-114k, depth 0 (dispatch) | 59.0 s, 554 MB | 1.75 s, 90 MB |
| import synthetic-114k, depth 0 (session) | 44.8 s, 554 MB | 1.96 s, 90 MB |
| toggle on it (dispatch, 38.5 MB text) | 56.4 s, 346 MB | 0.70 s, 114 MB |
| toggle on it (session) | 49.9 s, 519 MB | 0.06 s, 20 MB |
| direction on it (session) | 15.1 s, 541 MB | 0.001 s, 0 MB |
| import full-3000, laid out whole | 5.5 s, 284 MB | 0.02 s, 2 MB |
| overview synthetic-114k | 10.2 s, 633 MB | 0.13 s, 83 MB |
| import code-100000, depth 0 (17 boxes) | 1.1 s, 277 MB | 1.00 s, 77 MB |

The estimate reads the request as the operation does, so through `dispatch` its cost is that reading plus the
projection; in a session, where the snapshot and its structure are kept, it is nearly free. An import with a small first
view of a large graph costs almost as much to estimate as to run (code-100000): the selection is the work there.

## Found on the way (fixed here)

- `dispatch_streaming`, which the WASM module's `lw_run` calls for every request, read each request into a JSON value
  only to see whether it was a progressive refinement. Only a request that names `refineProgressive` is read so now
  (answers unchanged). WASM, `dispatch` import at limit 100, depth 0: synthetic-20k 145.4 → 97.2 MB of linear memory
  (counted 115.5 → 75.3 MB), synthetic-2k 13.8 → 8.9 MB (same module built with and without the change; load about 40).

## Not changed, for later

- A stateless edit through `dispatch` reads the request into a JSON value before its types (`Request::from_json_delivered`):
  in WASM about 15 to 18 bytes per byte of snapshot text. Reading a snapshot request in one pass, as the import and a
  session's `load` already do, would lower that peak.
- A session's edit peaks above the same edit through `dispatch` (114k first view, `direction`: 541 MB against 339 MB),
  although it reads no snapshot: it clones the snapshot and lays out with the kept structure. Not investigated here.
